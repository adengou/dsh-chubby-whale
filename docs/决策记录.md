## ADR-0001 跨平台优先于单平台优化

- **决策**：任何改动先保证 Windows / Linux / macOS 行为一致；只在某一平台才成立的优化，必须写成「平台分支 + 保守回退」，并在 `docs/跨平台与分工.md` 记一行。
- **理由**：插件是给多平台宿主用的（README 明确三平台），Windows-only 的假设会变成 Linux 上的静默坏数据。
- **证据**：`docs/跨平台实测-20261106.md` 的实测结论；`src/host/atomic.ts` 的「先写临时文件再 rename」在 Windows 上有目标存在时的语义差异，必须显式处理。
- **代价**：某些优化会慢一点（比如不做 mmap、不做 rename-overwrite 的特快路径）。
- **推翻条件**：宿主明确只在单平台分发。

## ADR-0002 模块只暴露接口，禁止跨模块读内部状态

- **决策**：每个模块对外只给 `createXxx(deps)` 工厂 + 明确的类型；路由层只经注入端口（ports）工作，不允许 `import` 仓储内部状态、不允许值级再导出业务数据。守卫脚本：`scripts/check-boundaries.mjs`、`scripts/check-imports.mjs`、`node scripts/gen-module-index.mjs --check`。
- **理由**：两次真实事故都是「薄路由/薄模块顺手把内部状态当 API」，改动一处连带踩坏另一处。
- **代价**：新增能力要走「加端口 + 装配层注入」，比直接 import 慢一步。
- **推翻条件**：无（这是架构宪章级约束，见 `docs/架构宪章.md`）。

## ADR-0003 说书 `isLast` 保持「整本讲完才为真」，不做「最后一章即讲完」

- **决策**：`isLast = endsBook && piece >= total` 维持现状（`src/host/story/player.ts:392`）。**不**改成「本书最后一段就置真」。
- **理由**：
  1. 客户端把 `isLast === true` 当「**整轮讲完**」处理 —— 关连播 + 报「讲完了」（`src/client/story.ts:30`、`:380` 附近）；而服务端一轮讲完会自动回卷重来，「讲完一本接着讲下一本」是既定行为（`player.ts` 头注释第 34–37 行写明）。
  2. 数据里**没有 `piece` 字段**（17 本实测只有 `total`），所以 `piece >= total` 实际等价于「回内单段」。把它放宽成 `endsBook` 会让 16 本书在**每本结尾**都触发「讲完」并停掉连播 —— 这是行为变更，不是修 bug。
  3. 「这一回讲完了」的提示已由 `endsChapter` 单独负责（`player.ts:379` 的结尾句），不需要 `isLast` 兼职。
- **代价**：17 本书里只有《杨家将演义》（末段 `total===1`）会走「整本讲完」分支；其余书结尾靠回末提示 + 自动回卷。
- **推翻条件**：主人明确要「每本讲完停一下」；届时改 `isLast` 并同步改客户端「讲完」文案与 `test-story-player/host/client` 三处断言。

## ADR-0004 `start` / `next` 是带副作用的 GET，但**不**强制 `x-client-id`

- **决策**：保持「GET + 查询参数」的既有契约，不把 `x-client-id` 变成硬性要求。
- **理由**：服务端确实读 `x-client-id`（`src/host/routes/story.ts:39`）并用它做「谁领走的段」与断连回队；但既有回归 `scripts/test.mjs` 有大量不带该头的直连调用，把缺头判 400 会让这些用例全红，而这些用例锁的是**既有对外契约**。真正的防护已经由两件事覆盖：① 进度改成「响应送出后才 confirm」（B97），预取/中断不会误记；② 客户端在途请求可中止（B98）。
- **代价**：爬虫/预取仍可能「顺手推进度」；但推不进度只在响应真的送达时才会发生，而 GET 返回的是**正文**，等价于真的读到内容。
- **推翻条件**：出现真实的外部预取把进度推花的证据；届时新增 `POST /story/pick` 并保留 GET 只读的兼容层，不直接收紧 GET。

## ADR-0005 版本号只增不改；漏发的版本**不补发**

- **决策**：已打的 tag 不移动（除非发布事故且远端未扩散，见 ADR-0006）；某个版本若只发到了部分渠道（例如 1.1.75 只在 Gitee），**不补发**到剩余渠道，由下一个版本覆盖。
- **理由**：补发会造成「同名版本在不同渠道内容不同」或「latest 回退」，比缺失更危险；用户装 `latest` 永远拿到最新，不会踩到缺口。
- **证据**：1.1.75 只推到 Gitee（Gitee tag 存在）；npm 版本序列 `…1.1.74 → 1.1.76`（npm 无 1.1.75），GitHub 仅 1.1.76。原因：主人在发布窗口插入「提醒清单 BUG」修复，同步步骤未执行。
- **代价**：版本序列不连续，需要在 CHANGELOG 里能查到即可。
- **推翻条件**：主人明确要求某版本必须在三渠道都可安装。

## ADR-0006 发版前必须过一致性自检；坏 tag 允许「删除重建」

- **决策**：推远端之前跑 `npm run check-release`；打完 tag 再跑 `npm run check-release:strict`。若发现 tag 指向的提交里 `package.json` 版本与 tag 不一致（坏 tag），**允许**删除并重建该 tag，远端用 `git push -f origin <tag>` 覆盖 —— 前提是 npm 尚未发布该版本（npm 版本不可删除）。
- **理由**：2026-11-07 真实发生过一次：发布脚本语法错误导致后续 `commit/tag/push` 照常执行，打出「tag=v1.1.72、package.json=1.1.71」的坏 tag 并推到 Gitee；npm 未发，删除重建后三端一致。
- **证据**：`tools/check-release.mjs`（五处核对）；`docs/发布规范.md` 第五之二节。
- **代价**：极少数情况下要 force-push tag（tag 引用被覆盖，历史提交本身不改）。
- **推翻条件**：CI 化之后由流水线强制拦截，不再依赖人工跑。

## ADR-0007 外部接口只读、拿不到就如实说「没读到」，绝不编内容

- **决策**：诗词 / 对联 / 文化 / 说书 / 简报等外部数据源，取不到就返回空（`item:null` / `titles:[]` / `songs:[]` / `no-data`），绝不用内置文本冒充外部结果。
- **理由**：这是主人定的第一铁律（不许编），也是客户端文案「这个没读到 / 诗册没读到」的对齐口径。
- **证据**：B102 审计用「关闭端口」的假服务实测三读口均如实返回空（`scripts/test-culture-source.mjs` 的 C2/C4）；`routes/culture.ts` 未知类型只回固定提示。
- **代价**：离线/断网时功能变少（但不会给错内容）。
- **推翻条件**：无。

## ADR-0008 不重启 dsh web；宿主侧改动「重启后生效」要在文档里写清

- **决策**：任何迭代都不重启主人正在用的 dsh web。宿主改动统一登记到 `docs/待重启生效.md`（每批一节，带「怎么验证」），并且在报告里如实说明「运行中的实例还是旧版本」。
- **理由**：主人第一原则；同时避免「改了但没生效」被误当成没修好。
- **代价**：修好的东西要等下一次重启才在运行实例里生效。
- **推翻条件**：主人明确要求立即重启验证。

## ADR-0009 气泡五线路模型（poem > voice > main > persona > tool）

- **决策**：气泡调度器按**五条线**排序——诗词线 `poem`(5) > 语音线 `voice`(4) > 主气泡 `main`(3) > 问候线 `persona`(2) > 解说线 `tool`(1)，每条线一个独立 DOM 元素。念诗正文/逐句进度走诗词线并采用「同道替换」（新一句顶掉旧字幕，不排队）；语音识别状态走语音线并标 `transient`（被更高优先级压掉后不再补播）。
  - 语音线放在主气泡**之上**（2026-11-13 实测修正）：按 `main > voice` 排时，上一轮回复气泡还在（6 秒），「（听到）…」只能排队、4 秒后过期，主人从来看不到。语音是新一回合的即时确认，必须先出；被它顶下的回复气泡按原优先级回队列，语音跑完继续显示。
- **理由**：旧实现只有四条线（注释与提交信息写的「三线路」还漏了 persona），语音状态挤在主气泡线。语音问「背诵」时，「（听到）…」「（点播）好，念一首」「念诗标题」「逐句字幕」全按主气泡排队（3+3+15+8×N 秒），字幕比声音慢几十秒；没有语音线时「（听到）…」还会在整首念完后补播。五条线是主人 2026-11-13 校正的口径。
- **证据**：`src/client/bubble-queue.ts` 的 `LANE_PRIORITY`；`src/client.ts` 的 enqueue 接线（main/persona/poem/tool + 新增 voice/poem 替换）；`scripts/test-bubble-queue.mjs`（22 项：五线顺序、同道替换、瞬时丢弃）；`scripts/test-client-glue.mjs`（点播「背诵」/书名号/库外不凑数）。
- **代价**：页面上最多五个气泡元素（同一时刻只有一条活）；新增线路要同时改调度器、CSS、渲染三处。
- **补充（2026-11-13 同日）**：硬不变量是「**任何时刻只有一条气泡活着**」，由 `startItem` 统一持有 current + 定时器，所有路径（首次入队 / 抢占 / 同道替换 / 合并键）都先停后起；`test-bubble-queue` 用 80 条混合入队断言 `maxAlive=1` 钉住。为此调度器补齐三条策略：① 流式片段用 `key` 合并（同线同 key 只留最新，避免每 400ms 一条 3 秒气泡把主气泡线拖成回放队列）；② 瞬时状态用 `staleAfter` 过期（等 4 秒还没轮到就不补播）；③ 队列上限 `MAX_QUEUED=64`（溢出丢最早的最低优先级）。
- **补充（2026-11-13 同日 · 全面审查）**：五线模型定稿后按「串线 / 占线 / 抢线」审查了一遍生产者接线，修了三处：① 说书段标题改走诗词线（同道替换，不再被字幕顶下后插回）；② 被抢占条目**沿用首次入队时间**（`staleAfter` 不因抢占而续命）；③ 主气泡默认 20 秒过期、弹幕单条上限 18s→12s。审查记录见 `docs/气泡线路审查-20261113.md`。
- **推翻条件**：主人认为五条线太多、要求合并（例如把语音状态并回主气泡线）。
