## 五、结论

1. **短时观测没有发现内存泄漏迹象**：8 分钟两轮采样，内存走平或微增（≤0.2%），私有内存不动。
2. **磁盘缓存会随使用增长**，tts 已达 775 个文件 / 24.3MB，**离「800 个触发清理」只差 25 个文件**。
   触发时会按 mtime 删掉最旧的一半（约 400 个）——这是设计行为，不会报错，但会让这些音频下次重新合成。
3. **1118MB 是整个 dsh web 进程**（含全部插件、MCP 服务等），**不能据此认定本插件占多少**；
   要精确归因需要单独起一个只装本插件的实例做对照，本次没有做（避免干扰主人的实例）。

## 六、局限（如实说明）

```
· 只见进程级内存，看不到 V8 堆内部（未连 inspector）
· 观测窗口仅 8 分钟，不足以判定"整夜""整天"的长期趋势
· 期间有没有人说话/点播不受控制，缓存增长速率只是"当时"的快慢
· 没有做"卸载插件"的对照实验（需要改配置+重启，违反本次只读原则）
```

## 七、建议（等主人决定，不擅自改）

1. **磁盘清理阈值**：目前 800 个文件就清一半。若主人常听说书，可以把 `MAX_FILES` 提到 1200，
   代价是磁盘多占约 10MB，收益是少重复合成、少花 TTS 额度。
2. **重启后复测**：主人下次重启 dsh web，可以照本文方法再跑一次，对比"刚启动"与"跑几小时后"的曲线。
3. 若想要更精确的归因：另起一个只装本插件的 profile 做对照测量（需要主人同意再动配置）。
