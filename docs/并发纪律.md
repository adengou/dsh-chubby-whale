# 并发与异步纪律（防串线 / 占线 / 插队）

> 2026-11-04 建立。语音插件最容易出的一类问题不是功能缺失，而是**多条异步链互相踩**。
> 这份文档定义"谁先谁后、谁能打断谁"，改代码前先对照。

## 一、三类真实故障（都是并发没管好）

| 现象 | 本质 | 触发场景 |
| --- | --- | --- |
| **串线** | 旧请求的响应回来盖住了新请求的结果 | 主人连说两句，第一句的回答晚到，把第二句的回答冲掉 |
| **占线** | 某个"锁"没释放，后续永远进不去 | 识别请求异常返回，占位标志没清 → 耳朵永久哑掉 |
| **插队** | 低优先级任务抢了高优先级任务的话筒 | 提醒铃声突然插进说书中间 / 老答案插进新回答 |

## 二、资源与优先级

插件里只有三个真正稀缺的资源，其余都只是状态：

```
① 麦克风（同一时刻只能录一段）
② ASR 通道（同一时刻只允许一个识别请求在途）
③ 扬声器（同一时刻只能播一段语音）
```

任务优先级（**数字小的优先级高，只有高优先级能打断低优先级**）：

| 级别 | 来源 | 能否打断别人 |
| --- | --- | --- |
| P0 | 主人提问（打字 / 语音） | 可以：打断说书、念诗、任何朗读 |
| P1 | 说书 / 念诗 / 讲故事 / 讲典故 / 讲成语 | 可以打断 P2，被 P0 打断 |
| P2 | 定时提醒 | 不打断任何东西，**排队等空闲** |

## 三、五条硬规则

### 规则 1：对话请求带纪元（防串线）

```ts
const myEpoch = ++chatEpoch
const data = await fetch('/api/chubby-whale/chat', ...)
if (myEpoch !== chatEpoch) return      // 主人已经问了新问题，这条旧回复作废
```

`chatEpoch` 每次发起对话自增。回来的响应的纪元对不上，就**不写进对话、不出声**。

### 规则 2：识别请求单飞（防乱序）

```ts
if (asrBusy) return        // 上一段还没识别完，这段直接丢
asrBusy = true
try { ... } finally { asrBusy = false }   // 无论成功失败都要放，否则耳朵永久占线
```

宁可丢一段音频，也不能让两段音频的识别结果乱序返回。

### 规则 3：占线保护（防重复提问）

```ts
if (busy) { showBubble('本鲸还在想上一句呢，稍等～'); return }
```

`busy`（正在等对话结果）期间不接受新提问，而不是排队 —— 语音场景下排队会让用户以为"它卡了"。

### 规则 4：只有 P0 能打断（防插队）

- 主人提问 → 先 `stopTts()` 掐掉正在播的旁白，再回答；
- 提醒（P2）→ 发现 `ttsPlaying || ttsQueue.length > 0 || storyNarratingRef.current || busy` 就**等 2 秒再看**，绝不插进别人中间；
- 说书/念诗（P1）→ 不主动打断任何人，只被 P0 打断。

### 规则 5：说话期间不录音（防自言自语）

```
ttsPlaying || ttsQueue.length > 0 || storyNarratingRef.current  → 麦克风一律不上传
TTS 结束 → 再等 700ms（ECHO_MUTE_MS）让混响散掉
ASR 结果与本鱼最近说过的 6 句做相似度比对 → 命中即判回声丢弃
```

   > 2026-11-07 补充（B84）：叙述锁现在**按持有者令牌归属**——`clearNarrate()` 只在仍是自己持有时才清锁，
   > 旧段 onDone（TTS 串行排队，天然晚到）不会再把新使用方的锁解掉；「停止说话」与过期看门狗走权威清锁。
   > 想读长段朗读是否卡住：看 `__chubbyWhale.narrateOverdue` / `narrateOverdueInfo`（只报警，不动锁）。
## 四、状态机

```
          ┌──────── idle ────────┐
          │                      │
  用户说话│                  TTS 播完
          ▼                      │
      thinking ──(回复到达)──► speaking
          │                      │
          └──(P0 打断)──────────► idle
```

- `idle` → 唯一接受新提问的状态；
- `thinking` → 只等当前纪元的响应，其它一律丢弃；
- `speaking` → 麦克风关闭；P0 提问可强制回到 thinking。

## 五、自检清单（改并发相关代码时逐条过）

```
[ ] 每个 await 之后，有没有校验"我还是当前那个请求"（纪元/序号）
[ ] 每个 try 都有配对的 finally 释放占位标志（asrBusy / busy / storyNarrating / ttsPlaying）
[ ] 低优先级任务（提醒）会不会抢高优先级的话筒
[ ] 打断别人之后，有没有把对方的状态标志一起清掉（否则会卡在"正在说书"）
[ ] 定时器（setTimeout / setInterval / rAF）在卸载时是否清理
[ ] 队列有没有上限？（无上限的队列在断网时会无限堆积）
[ ] 同一件事会不会被触发两次（HMR、重复点击、两次 pointerdown）
```

## 六、已知限制（不粉饰）

- **没有真正的任务队列**：P1/P2 用"空闲轮询 + 标志位"实现，不是调度器。极端情况下（连续多次提醒）仍会串行播报，只是不会互相打断。
- **恢复性打断有代价**：P0 打断说书后，说书的进度停在当前段，需要主人点「接着说」继续。
- **纪元机制覆盖对话与 ASR**（2026-11-07 起）：说书进度、提醒仍各用自己的标志，没有统一事务。
  对话走 `chatEpoch`，ASR 走 `asrEpoch`（start/stop/stopSpeaking 各 +1，await 后逐个校验）；两者互不覆盖，
  但都要遵守同一条：**过期结果不许再改任何状态**。
- 并发问题难用自动化测出来（需要真实麦克风 + 真实网络抖动），本文的规则来自实际故障复盘，**未做压力测试**。

## 七、"要不要一个全局单线程队列？"——不要，要三条资源通道（**设计稿，尚未实现**）

> 2026-11-07 更新（B95）：**基础件已落地** —— `src/client/channel.ts` 提供 `createChannel()`：

> 由 `scripts/test-channel.mjs`（22 项断言，已接入 `npm test`）验收。
>
> **仍未接入**：`mic` / `asr` / `speak` 三条资源目前还是各模块自己的标志位（录音段排队 + `ttsQ`
> 串行播放 + ASR 段号去重），`client.ts` 的 `channels` 诊断对象仍恒为空。接入要逐个资源替换
> 现有串行逻辑并重跑并发断言，属独立一批，别为「用上新件」而硬套。

浏览器 JS 本来就是单线程，所以"单线程"不是选择，是既定事实。真正要选的是**排队粒度**。

**全局 FIFO 队列的问题**：一个 2 秒的对话请求会把提醒、气泡、动画全堵在后面，
用户看到的是"整个插件卡死"。而这三件事本来互不相干。

**正确的粒度是"每个独占资源一条通道"**（见 `src/client/channel.ts`）：

| 通道 | 独占资源 | 策略 |
| --- | --- | --- |
| `mic` | 麦克风采集段 | conflate：同 key 只留最新一段 |
| `asr` | ASR 请求 | 串行 + 忙则丢（结果不能乱序） |
| `speak` | 扬声器 | 串行 + 优先级（P0 回复 > P1 说书 > P2 提醒） |

通道内严格串行，**通道之间并发**。这样：
- 说话不会因为动画卡住而漏听；
- 说书不会因为提醒排队而停住；
- 主人回复不会被旧旁白堵住。

### 队列与纪元的分工（容易搞混）

```
队列负责"谁先执行"   —— 资源只有一个，必须排队
纪元负责"结果算不算" —— 过期的结果不该排队，应该直接丢
```

两者缺一不可：只有队列 → 旧结果照样执行；只有纪元 → 结果乱序到达。

### 单元测试（**未实现，下面的数字是设计目标，不是实测**）

```
实测1：阻塞期间塞 P3 → P1 → P0 → P2，放行后执行顺序 P0 → P1 → P2 → P3
实测2：conflate A 在跑时塞 B、C   执行 A → C，B 被丢弃（dropped=1，旧调用方 rejected 收口）
实测3：同步抛错的任务不会卡死队列（failed+1，后续任务照常）
实测4：两条通道可同时跑（maxOverlap=2），证明不是全局串行
```

> 上述四条的实现与断言在 `src/client/channel.ts` / `scripts/test-channel.mjs`（2026-11-07 落地）。

### 什么不该进队列

- 渲染 / 动画：走 rAF，进队列只会抖；
- 状态更新（setState）：同步语义，排队会撕裂 UI；
- 网络读接口（余额、诗、故事）：彼此独立，并发即可，只对"最新一次"做纪元校验。
